1. Product contract: what is being built

The supplied concept proposal defines an AI safety layer around existing surveillance infrastructure. Its operating idea is Detect → Verify → Alert: analyze configured video streams, surface high-risk visual events, and require human confirmation before serious escalation.

Required event family

Visible weapon, physical altercation, restricted-zone entry, person down, loitering, and abnormal crowd movement are the proposed initial high-value detections.

System shape

Existing cameras / RTSP / ONVIF / VMS → AI gateway → models + confidence + rules → human verification → alert / response.

Architecture direction

Hybrid edge / on-prem inference is the proposed direction, with local buffering and selected events / metadata sent to the application layer.

Operational features

Security dashboard, incident timeline, RBAC, audit logs, integrations, configurable retention and privacy zones are part of the target platform shape.

Important distinction: the proposal contains pilot goals such as 99.9% uptime, 90%+ camera compatibility, ≤5 s alert delivery and a 30 s critical-event review target. Those are proposed design goals, not measured results. They must not be presented as achieved until tested.

1.1 Scope for this engineering plan

This plan assumes the internship deliverable must implement the complete product surface, but may use practical shortcuts where the proposal is architectural rather than prescriptive. The system should be real enough to demonstrate end-to-end behavior and structured so a later production team can replace individual components without rewriting the system.

1.2 Non-negotiable product behavior

  • The AI produces potential incidents; it should not silently become an autonomous emergency decision-maker.
  • Every event must be traceable to a camera, time range, model/rule path, confidence and stored evidence.
  • A camera source must be replaceable without changing the CV logic.
  • One slow camera must not freeze other cameras.
  • One bad frame, broken stream, model exception or notification failure must degrade that component without taking down the whole service.
  • Multiple users must be able to review different incidents concurrently without corrupting state.

Each sprint should leave the repository in a runnable state. Do not create a six-week “CV branch” that cannot be demonstrated by anyone else.

2.2 What to build first

  1. Runtime skeleton: configuration, logging, health checks, database, API, basic UI shell.
  2. Thin CV slice: video input → person detection → event object.
  3. Incident slice: event → evidence clip → API → dashboard → verify / dismiss.
  4. Tracking and rules: turn raw detections into useful events.
  5. More threat modules: person down, fight, crowd, weapon.
  6. Infrastructure hardening: RTSP, multi-camera isolation, queues, concurrency, auth, privacy, audit, load testing.

2.3 The “learn while shipping” rule

Learn only what unlocks the next implementation

Before implementing tracking, learn IoU, data association and track lifecycle. Do not spend days on unrelated CV theory.

Read model documentation yourself

You must know what inputs, outputs, confidence values, classes and limitations your model has. Do not treat generated code as understanding.

Write a tiny experiment first

For every unfamiliar CV technique, make a small reproducible notebook/script before integrating it into the main system.

Promote experiments only after tests

Prototype code can be messy. Production modules need types, error handling, logging, configuration and tests.

2.4 Timeboxing

Every sub-sprint has three clocks: learning clock, implementation clock, and integration clock. When a learning topic starts consuming the sprint, reduce scope of the feature—not testing and not integration.

4.2 Separate observations from incidents

A bounding box is not an incident. A track is not an incident. This distinction is central to the design.

Observation

“Person detected at x,y,w,h with confidence c at timestamp t.”

Track

“These observations are probably the same person across frames.”

Incident candidate

“Track #17 satisfied the restricted-zone rule for the configured policy.”

4.3 Model strategy

  • Use a small pretrained detector as the default development model. Do not train a detector from scratch.
  • Prefer deterministic geometry and temporal rules where they solve the problem reliably enough.
  • Use tracking as the common state layer for multiple threat modules.
  • Fine-tune only when baseline models demonstrably fail on the target camera environment.
  • Keep model weights outside source control and load them from a configured model directory or artifact location.

4.6 Performance strategy

Do not automatically infer at camera FPS. Separate decode rate, inference rate and display rate. Example: a 25–30 FPS stream may be decoded continuously while inference runs at a lower target rate and the tracker fills gaps.

The exact target must be measured on the available machine and camera resolution. Keep the inference policy configurable per camera.

5.3 API rules

  • Every list endpoint is paginated.
  • Every mutating endpoint validates input and returns stable error structures.
  • Do not put long-running CV work inside an HTTP request.
  • Idempotent actions should be implemented where retries are expected.
  • Use UTC timestamps in storage; convert to local time only at presentation.
  • Never log passwords, tokens, stream URLs containing secrets, or raw notification credentials.

  4. Incident detail: event clip, snapshot, context, confidence, detection timeline, actions.
  5. Administration: users, roles, cameras, zones, rules, retention.

6.4 Idempotency and deduplication

Threat detection naturally produces repeated frames describing the same event. Create an event signature such as camera + event_type + track_id + time_bucket, then apply cooldown and merge logic. The goal is one human-reviewable incident instead of hundreds of identical alerts.

6.5 Retention

Evidence must have a lifecycle: created → reviewable → retained for configured duration → deleted. Retention should be a configuration, not a hard-coded forever policy.

8. Detailed sprints and sub-sprints

S0 — Engineering foundation

BLOCKER

0A — Repository and standards

Define repository layout, Python environment, frontend environment, code formatting, linting, type-checking policy, commit style, environment variable conventions.

Exit: another developer can clone and run basic checks.

0B — Configuration and secrets

Create typed configuration for DB URL, model path, media directory, log level, allowed origins, retention values and notification settings. Use an environment file only for local development; never commit secrets.

Decision: application config is code-readable; secrets are external.

0C — Database and migrations

Create initial schema and migration process. Use Postgres for multi-user environments; permit SQLite only as a developer convenience if necessary.

Exit: migration up/down or forward migration is documented.

0D — Logging and health

Structured logs with request IDs and camera IDs. Add liveness and readiness endpoints. Define what is safe to log.

Exit: a failing DB is visible in readiness without crashing the API process.

Learn: why configuration, dependency injection, migrations, structured logging and health checks exist. You should be able to explain each one before moving on.

S1 — First vertical slice: video to verified incident

SHIP EARLY

1A — Video reader

Build a common VideoSource interface with file and webcam implementations. Emit frames plus source timestamps. Add end-of-stream and reconnect states.

1B — Detector adapter

Wrap the chosen pretrained detector behind Detector.detect(frame). Normalize its output into your own internal Detection schema.

1C — Event adapter

For the first thin slice, generate a simple person-presence or test event with confidence and evidence metadata. Do not bury business logic inside model code.

1D — API + dashboard

Create incident endpoint, incident list, incident detail, and a verify/dismiss UI. Use polling first; real-time push can come later.

Definition of done: upload an MP4, run the worker, create an event, show it in the dashboard, verify it, and see the action recorded.

S2 — Tracking core

CV CORE

2A — Tracking experiment

Measure how the selected tracker handles occlusion, crossings and short disappearances. Visualize track IDs and trajectories.

2B — Track lifecycle

Implement new → active → temporarily lost → terminated states. Add max-age / grace periods as configuration.

2C — Camera-local state

Keep tracks scoped to a camera session. Never assume a track ID is globally unique across cameras.

2D — Test fixtures

Create short reproducible clips for single person, two persons crossing, partial occlusion and re-entry.

Learn: detection is frame-local; tracking builds temporal identity. Understand association and why identity can be lost.

S3 — Restricted zones and loitering

FIRST REAL VALUE

3A — Zone editor

Allow an admin to define polygon zones on a camera frame. Persist vertices and metadata.

3B — Entry / exit logic

Use a stable point from the track (typically a bottom-center point) and point-in-polygon checks. Add boundary hysteresis to prevent flicker.

3C — Loiter timer

Track continuous residency time. Define whether “brief exit” resets the timer or receives grace time.

3D — Incident dedup

Merge repeated frames into one incident. Add cooldowns so a zone breach does not produce hundreds of notifications.

Design choice: make thresholds per rule and per camera. Do not scatter magic numbers through Python code.

S4 — Evidence and event clips

OPERATIONS

4A — Rolling frame buffer

Maintain a bounded in-memory or short-term disk buffer per camera. Its size must be configurable.

4B — Clip writer

When an incident opens, preserve pre-event frames and continue capturing post-event frames, then encode a bounded clip asynchronously.

4C — Storage abstraction

Define EvidenceStore so local filesystem storage can later become object storage without API changes.

4D — Secure media access

Serve clips through authorized endpoints. Do not expose arbitrary filesystem paths or public directories.

Exit: every test incident can be opened, watched and traced back to its source camera/time.

S5 — Person-down detection

BEHAVIOR

5A — Define the event operationally

Write the actual rule before coding: what counts as down, how long it must persist, and which states should be excluded.

5B — Baseline geometry

Use bounding-box aspect ratio, center movement and persistence as a baseline. Measure failure cases instead of assuming the heuristic works.

5C — Optional pose model

If geometry is weak, test pose landmarks or another pretrained approach. Compare complexity and false alerts.

5D — Scenario evaluation

Test standing, sitting, crouching, intentional lying down, actual fall, partial occlusion and multiple people.

S6 — Physical altercation

HARD

6A — Pair features

For nearby tracked people, calculate center distance, relative velocity, movement magnitude and short-window changes.

6B — Temporal rule

Use a rolling time window rather than frame-by-frame decisions. Require persistence and multiple signals.

6C — Scene calibration

Define per-camera thresholds. What is suspicious in a corridor may be normal in a sports area.

6D — Evidence review

Always attach the clip and show the time window used by the rule. The UI should make it clear this is a potential altercation event.

Do not overclaim: unless evaluated on representative footage, call this “potential physical altercation” rather than implying perfect understanding of human activity.

S7 — Abnormal crowd movement

ANALYTICS

7A — Crowd features

Aggregate active track count, mean speed, direction dispersion, pair distances and zone density.

7B — Baseline

Store short-term baselines per camera and time window. A campus entrance at 8 AM is different from a parking area at midnight.

7C — Anomaly score

Start with a transparent weighted score rather than a black-box model. Log each feature contributing to the score.

7D — Threshold tuning

Replay known clips and inspect false alerts. Make the score and thresholds configurable.

S8 — Weapon detection

DATA / MODEL

8A — Baseline model audit

Check whether a pretrained model supports the needed weapon classes. Measure failures on representative footage before deciding on fine-tuning.

8B — Dataset design

Build a labeled dataset split by scene, source and time. Avoid near-duplicate frames leaking between train and test.

8C — Fine-tune if necessary

Only after baseline failure is understood. Track model version, dataset version and hyperparameters.

8D — Temporal confirmation

Require evidence across a short window when appropriate; reduce single-frame alerts caused by noise or partial views.

Exit: report measured precision/recall or another justified evaluation on a held-out set; do not use training-set accuracy as the headline result.

S9 — Operator dashboard and concurrency

PRODUCT

9A — Incident list

Pagination, filters, sorting, server-side queries. Never load all incidents into the browser.

9B — Review workflow

Open → review evidence → verify/dismiss. Prevent stale actions with optimistic concurrency or row-version checks.

9C — Two-user test

Simulate two operators reviewing the same incident. The second action must be handled predictably.

9D — Real-time updates

Polling is acceptable first. Add WebSocket/SSE only after the core workflow is stable.

S10 — Security, RBAC, audit and privacy

REQUIRED

10A — Authentication

Implement credential validation, password hashing, session/token policy and logout/revocation strategy appropriate to the deployment.

10B — Authorization

Enforce role checks server-side. UI hiding is not authorization.

10C — Audit log

Record logins, incident views where policy requires, verification/dismissal, camera changes, rule changes and administrative actions.

10D — Privacy zones

Persist camera privacy polygons and verify masking behavior in stored evidence. Define whether masking occurs before inference, after inference, or both for each policy.

S11 — RTSP and multi-camera execution

SCALE

11A — RTSP source

Implement connection lifecycle, reconnect with exponential backoff, stream timeout detection and bounded queues.

11B — Per-camera worker state

Isolate errors and resource accounting per camera. Each stream should expose health metrics.

11C — Backpressure

Choose a deliberate policy: drop old frames and process recent frames rather than allowing an unbounded queue to consume RAM.

11D — Camera fleet test

Simulate several streams using repeated files or generated RTSP sources. Measure throughput, memory and recovery after a stream failure.

Key production rule: the system should fail locally. If Camera 4 dies, Cameras 1–3 and 5–N should keep operating.

S12 — Reliability, load and failure hardening

PRODUCTION GATE

12A — API load

Measure concurrent reads, incident list filtering, media access and auth operations. Look for slow queries and connection pool exhaustion.

12B — Worker saturation

Measure GPU memory, inference latency, queue depth, dropped frames and event latency as camera count increases.

12C — Failure injection

Kill/restart DB, stop a camera, fill the media disk, break notification credentials, restart workers and verify graceful recovery.

12D — Data integrity

Verify incidents are not duplicated after retries and review actions are not applied twice.

Exit: known capacity limit, known failure behavior, reproducible load test and documented recovery procedure.

S13 — Release and handover

SHIP

13A — Staging environment

Fresh environment with representative data and cameras. No developer-only paths.

13B — Production config

Secrets, database, storage path, model artifact versions, allowed origins, admin bootstrap and log rotation.

13C — Runbook

Start/stop, health checks, camera troubleshooting, disk cleanup, incident recovery, backup/restore and model rollback.

13D — Demo protocol

Prepare deterministic clips for every threat type. Every demo should have expected output, reset steps and known limitations.

Final exit: a clean installation, full smoke test and operator walkthrough can be completed without the original developer explaining hidden steps.

9. Testing and CV evaluation

9.1 Test pyramid

Unit

Geometry, rule evaluation, time windows, deduplication, serializers, permissions, state transitions.

Integration

Worker → event bus → DB → API → media storage. Test real transactions and failure behavior.

End-to-end

Known clip → expected incident → evidence → dashboard → verify/dismiss → audit record.

9.2 Computer-vision evaluation

Do not evaluate the project only by “the demo looked good.” Create a small, versioned benchmark set.

  • Positive cases: real target behavior.
  • Hard negatives: visually similar but non-threat behavior.
  • Edge cases: occlusion, lighting, crowding, camera motion, low resolution.
  • Different cameras: avoid testing only on footage used during development.
  • Temporal metrics: event latency, duplicate events per incident, time-to-clear after a false candidate.

9.3 Metrics by layer

DetectorPrecision, recall, class-wise AP/mAP where appropriate, inference latency.
TrackerID stability, lost-track rate, identity switches in the benchmark set.
Event rulesEvent precision, event recall, average duplicates per real incident, detection-to-event latency.

9.4 What not to claim

  • Do not claim “real-time” without measuring end-to-end latency under load.
  • Do not claim “production-ready” without failure tests and multi-user testing.
  • Do not claim “weapon detection accuracy” from a handful of demo clips.
  • Do not present proposed pilot targets from the concept document as achieved results.

11.3 Production direction

Start as a single-node deployment only if the actual pilot size allows it. The architecture must expose resource usage so the company can later decide whether CV inference needs a dedicated GPU node, whether the DB should move to a managed service, and whether the dashboard/API should scale separately.

11.4 Backup and restore

  • Database backup schedule must be explicit.
  • Important configuration must be backed up.
  • Evidence storage retention and backup must be treated separately from metadata backup.
  • A backup that has never been restored is an assumption, not a recovery plan.

11.5 Environment separation

Keep development, staging and production values separate. Model versions and rule versions should be explicit, so an incident can be traced to the software/model configuration that generated it.

12.1 How to use AI without outsourcing engineering judgment

Good use

Ask for implementation alternatives, test cases, edge cases, refactoring suggestions, explanations of unfamiliar APIs and code review.

Bad use

Paste a vague requirement and ship the generated architecture without understanding state, failure modes, data ownership or model limitations.

14. Definition of Done

14.1 Feature-level DoD

  • Feature has a clear input, output and failure behavior.
  • Configuration is externalized; no hidden constants for policy thresholds.
  • Unit tests cover core logic.
  • At least one end-to-end scenario exists.
  • Logs identify the camera/event/request involved.
  • UI exposes status and error states.
  • Documentation states known limitations.

14.2 Release-level DoD

All target modules wiredEvery proposed event type has an implementation path.
Evidence attachedIncidents have usable clips/snapshots.
Human review enforcedSerious alerts follow the intended verification workflow.
Failure behavior knownLoad and failure tests produce documented limits.

14.3 Demo acceptance checklist

  1. Start the stack from a clean environment.
  2. Show camera health.
  3. Run one deterministic clip for each detection module.
  4. Show incident generation and evidence clip.
  5. Verify one incident as Operator A.
  6. Show the audit record.
  7. Attempt an unauthorized action as a lower-privilege user.
  8. Disconnect one camera and show the rest of the system remains healthy.
  9. Show the system health page/logs and explain measured limitations.

15. Fast-track variants when the deadline changes

15.1 If you have roughly 2 weeks

Do not pretend all six CV modules are equally mature. Ship the complete application around detection, tracking, restricted zones, loitering and evidence; implement the remaining modules behind clean interfaces with deterministic demo scenarios and clearly labeled maturity. Prioritize end-to-end reliability over model sophistication.

15.2 If you have roughly 4 weeks

Complete the full application, RTSP, tracking, zones, loitering, person-down and at least one advanced behavioral module. Add a baseline weapon module and a proper evaluation set. Finish auth, RBAC, audit, privacy and load testing before polishing the UI.

15.3 If you have roughly 6–8 weeks

Complete the whole architecture above, then spend the remaining time improving dataset quality, event thresholds, camera-specific calibration, performance, operator workflow and deployment reliability. This is the point at which model fine-tuning becomes worth the investment if the baseline is clearly insufficient.

15.5 Recommended first working session

  1. Create the repository and directory structure.
  2. Containerize the database and local infrastructure.
  3. Create the VideoSource, Detection, Incident and Evidence interfaces/types.
  4. Run one MP4 through a pretrained detector.
  5. Persist one test incident.
  6. Display it in a minimal dashboard.
  7. Verify/dismiss it and write the audit event.

That first slice is the foundation. Once it works, every new CV capability becomes an incremental module instead of another rewrite.
